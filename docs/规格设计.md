# WHAT-TO-EAT-AGENT 规格设计说明书

**文档性质**：本文件为**开发与重构的唯一技术规格**（实现以此为准）。上位需求见 [`docs/项目说明.md`](项目说明.md)（SRS，需求修订记录当前至 **1.10**）。

**已定稿前提（摘录）**：

- 无登录；单机家庭；**作用域标识符**统一为本文 **SCOPE_ID**（默认 `default`），同时约束画像与库存。
- 菜谱 **R**（`recipe_requirements`）的**唯一权威来源**：在锁定 `file_ref` 后，读取**完整菜谱文件**正文并经 **阶段二解析管线**输出；禁止仅用向量检索片段拼接作为最终 **R**。
- 编排须 **意图分流、按需短路**，禁止固定全链路流水线。
- **R** 与 **I** 就绪后 **预计算**购物缺口并缓存；用户显式索要清单时 **优先返回缓存**（详见 §7）；扣减须在 **确认使用当前锁定菜谱** 之后（§6.3）；**补货**独立意图、预览后写库（§6.5）。

**SCOPE_ID**：配置键 `household.default_id`，默认值 `default`。画像库沿用列名 `user_id` 时，其取值 **必须** 等于 `SCOPE_ID`（迁移说明见 §8）。

## 1 系统总体架构

### 1.1 运行时组件

```text
┌─────────────────────────────────────────────────────────────────┐
│ Application（主进程）                                             │
│  LangGraph：conversation_summary → short_term → router → …       │
│  直达调用：RAGEngine / DocumentManager / InventoryManager / …     │
│  （可选）子进程：MCP Server（stdio），Agent 经 RecipeResearcher 调用 │
└─────────────────────────────────────────────────────────────────┘
         │ MCP JSON-RPC / stdio                     │
         ▼                                          │
┌──────────────────────┐                             │
│ MCP Server           │   search_recipes            │
│ recipe-researcher    │   get_recipe_source         │
└──────────────────────┘                             │
         │                                           │
         └── RAGEngine / DocumentManager / UserProfileManager
```

### 1.2 Agent 状态切片（实现必须收敛至此语义）


| 切片 key            | 字段（逻辑名）                                                                                                                               | 写入方                           |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| `dialog_state`    | 见 §1.2.0                                                                                                                             | 运行时 / checkpointer            |
| `memory_state`    | 见 §1.2.0                                                                                                                             | summary / short_term / keeper |
| `control_state`   | 见 §1.2.0（含 `task_stack`、`slots`、`missing_slots`、`confidence`）                                                                      | router / clarify / generator  |
| `recipe_state`    | 见 §1.2.0                                                                                                                             | researcher / clarify          |
| `inventory_state` | 见 §1.2.1（**I**、缺口缓存、清单编辑层、扣减/补货字段）                                                                                          | logistics                     |
| `response_state`  | 见 §1.2.0                                                                                                                             | generator                     |
| `error_state`     | 见 §1.2.0                                                                                                                             | 任意节点                          |


**方案 A**：`AgentState`（LangGraph 状态）采用 **顶层嵌套键**，上述七切片各为 **一个子对象**（`TypedDict` 或等价 dict 结构）；字段明细见 **§1.2.0**（通用切片）与 **§1.2.1**（`inventory_state` 展开）。  
迁移期允许扁平遗留字段与 `logistics_buffer` 并存，**新代码只读写切片语义**；由 **兼容层** 在读写时与 `logistics_buffer` / 顶层遗留字段做双向同步，直至删除废弃字段。

### 1.2.0 方案 A：`AgentState` 顶层切片与演进策略

#### 顶层形状（目标）

- **七切片**：`dialog_state`、`memory_state`、`control_state`、`recipe_state`、`inventory_state`、`response_state`、`error_state` — 均为 `AgentState` 的**一级键**。  
- **窄顶层字段（不计入切片）**：`active_user_id: str`，取值与 **SCOPE_ID** 对齐（单机无登录）；不放入 `dialog_state`，避免与消息语义混淆。  
- **消息归约**：`dialog_state.messages` 仍使用 LangGraph 推荐的 **`Annotated[..., add_messages]`** 归约；其余切片字段默认 **整对象替换**（或由实现显式定义 per-key reducer，须在注释中说明）。

#### `dialog_state`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `messages` | `List[BaseMessage]` + `add_messages` | L1 对话轨迹 |
| `thread_id` | `str`，可选 | 会话线程标识；缺省由运行时注入 |

#### `memory_state`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `conversation_summary` | `str` | L2 摘要 |
| `short_term_constraints` | `List[str]`（或结构化列表） | L3 当轮约束；与 SRS「当轮临时约束」一致 |
| `memory_confidence` | `float`，可选 | 当轮记忆抽取置信度 |
| `last_memory_update_at` | `str`（ISO）或时间戳，可选 | L4 / L3 更新时间审计 |

**迁移说明**：遗留字段 `active_constraints`（扁平）中的当轮有效内容 **应合并** 为对 `memory_state.short_term_constraints` 的写入，合并规则与 **C**（§3.5）一致；不得在迁移完成后双写长期真相。

#### `control_state`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `primary_intent` | `str \| None` | 与 `intents[0]` 一致 |
| `secondary_intents` | `List[str]` | 有序；多意图仲裁时次序有意义 |
| `task_stack` | `List[str]` | 与现有实现及 FR-04 一致；**禁止**再使用 `task_queue` 别名制造第二真相 |
| `current_task` | `str \| None` | 当前执行中的任务标签 |
| `needs_clarification` | `bool` | 低置信或缺槽时为真 |
| `loop_guard_count` | `int` | 防 generator↔route 死循环 |
| `is_continuation` | `bool`，可选 | 是否接续上一轮澄清/任务 |
| `slots` | `Dict[str, Any]` | 槽位填充结果（§12.2） |
| `missing_slots` | `List[str]` | 未填满的槽位名 |
| `confidence` | `float` | 本轮意图+槽位综合置信度 |

#### `recipe_state`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `recipe_file_ref` | `str \| None` | 阶段一得到的菜谱文件路径 |
| `recipe_candidates` | `List[Dict]` | 歧义候选 |
| `selected_recipe_title` | `str \| None` | 用户或系统锁定展示名 |
| `selected_recipe_id` | `str \| None`，可选 | MCP/检索侧 id，调试与追溯 |
| `recipe_requirements` | `List[Dict]` | **R**（权威结构化用料） |
| `recipe_steps` | `List[str]` | 步骤列表 |
| `recipe_title_locked` | `str \| None` | 锁定标题，与 `gap_basis.recipe_title` 对齐 |

**迁移说明**：原 `logistics_buffer` 内与菜谱相关的字段 **迁入** `recipe_state`；读侧经兼容层仍可暂时从 buffer 回填。

#### `response_state`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `final_response` | `str \| None` | 对用户可见主回复 |

**迁移说明**：原 `meal_plan` 等自然语言建议若仍单独存在，**应收敛**为写入 `final_response` 的一部分或合并至同一展示字段，避免与 `final_response` 双真相。

#### `error_state`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `error_code` | `str \| None` | 与 §9 枚举对齐 |
| `recoverable` | `bool` | 是否可重试/继续对话 |
| `error_detail` | `str \| None` | 内部或脱敏详情 |

#### 演进阶段（对实现约束）

1. **阶段 1**：在 `AgentState` 上 **新增** 七切片键（`NotRequired`/默认可空对象）；路由与各节点 **写入切片**；兼容层 **同步**旧 `logistics_buffer` 与顶层遗留键。  
2. **阶段 2**：各节点只通过 **访问器**（如 `get_recipe_state(state)`）读写，删除节点内对 buffer 键名的散落引用。  
3. **阶段 3**：移除 `logistics_buffer` 及已无读者的顶层冗余字段；checkpoint 迁移策略由实现单独立项（旧线程缺键时用默认空切片反序列化）。

### 1.2.1 `inventory_state` 字段（库存 + 缺口缓存 + 清单）

| 字段（逻辑名） | 类型（示意） | 说明 |
| --- | --- | --- |
| `inventory_snapshot` | **`Dict[str, {"amount": float, "unit": str}]`** | **I**：键为**规范化食材名**，值为数量与单位；与 §6、§7 计算口径一致；**禁止**使用 `List[Dict]` 作为该字段的最终形态 |
| `cached_shopping_gap` | 结构体，见 §7.2 | **R、I 就绪后预计算**的缺口结果；用户未索要清单时亦须写入 |
| `gap_basis` | `{ recipe_title, r_fingerprint, inventory_fingerprint }` | 判定缓存是否仍有效；任一指纹变化则缓存作废并须重算 |
| `shopping_list_overlay` | 操作列表，见 §7.4 | 用户对清单的增删改；与 `cached_shopping_gap` 合并后作为**对用户展示**的清单 |
| `recipe_use_confirmed` | `bool` | 用户是否已**确认使用**当前锁定菜谱（扣减前置条件，§6.3） |
| `commit_preview` / `commit_status` | 结构体 / 枚举 | **扣减**：预览与写库结果（§6.3～§6.4） |
| `add_preview` / `add_status` | 结构体 / 枚举 | **补货**：待入库预览与写库结果（§6.5） |

兼容名：实现可暂时沿用 `shopping_gap` 表示 **`cached_shopping_gap`**，但须在代码注释与状态中标注「缓存语义」。

### 1.3 板块调用次序（逻辑）

每轮用户输入：

1. **L1/L2/L3**（记忆）：消息追加 → 摘要按需 → 当轮约束写入 `memory_state`。
2. **意图**：router 产出 `control_state`；澄清则短路至 generator，不跑检索。
3. **偏好合并**：组装 **C**（§3.5），供菜谱检索消费。
4. **意图分流**：仅当任务需要时进入 **菜谱 / 库存 / 清单**。
5. **缺口预计算（静默）**：当 **R** 非空且已拉取 **I** 时，**logistics**（或等价节点）**必须**执行 §7.2 计算，写入 `cached_shopping_gap` 与 `gap_basis`；**不要求**用户本轮已表达清单意图，也**不要求**在回复中展开购物清单全文（与 FR-42 一致：禁止为凑流程而长篇打断）。
6. **L4**：主回复就绪后 **异步持久化**（§4.6）。

## 2 外部接口：MCP 菜谱工具（阶段一）

与仓库 `[src/mcp/server.py](f:/WHAT-TO-EAT-AGENT/src/mcp/server.py)` 对齐；实现变更须同步本文。

### 2.1 工具清单


| 工具名                 | 用途                                   |
| ------------------- | ------------------------------------ |
| `search_recipes`    | 阶段一：召回候选菜谱（RAG + 过滤），**不**产出权威 **R** |
| `get_recipe_source` | 阶段一补步：由菜名解析 `**file_ref`**（磁盘路径字符串）  |


### 2.2 `search_recipes`

**输入 Schema（JSON）**：

```json
{
  "query": "string，必填",
  "user_id": "string，可选，默认与 SCOPE_ID 一致",
  "top_k": "integer，可选，默认 5"
}
```

**成功响应（逻辑结构）**：

```json
{
  "recipes": [
    {
      "id": "chunk 或文档 id，字符串",
      "title": "展示用菜名",
      "score": 0.0
    }
  ],
  "query_used": "实际检索使用的查询串"
}
```

**说明**：`recipes[].id` 可用于调试；**锁定菜名**应以 `title` 与用户澄清结果为准，再以 `get_recipe_source` 取路径。

### 2.3 `get_recipe_source`

**输入 Schema**：

```json
{
  "recipe_name": "string，必填，与用户选定/系统锁定标题一致"
}
```

**成功响应**：MCP 层将返回值 `**json.dumps`** 封装为 `TextContent`。当前实现中 handler 返回 `**file_path` 字符串**（可为绝对路径）；也可能为 `**null`**（未命中）。

解析约定：

- Agent 侧收到 JSON 后若为 **字符串**，即为 `recipe_file_ref`。  
- 若为 `**null`** 或含 `**error**` 字段 → 置 `error_state`（如 `RECIPE_SOURCE_NOT_FOUND`，§9），**禁止** 捏造 **R**。

### 2.4 传输与错误

- 失败时响应体须含 `"status":"error"` 或 `"error"` 字段（与现有 server 行为一致）。  
- Agent **必须** 解析 JSON 后再分支，禁止假定返回值类型。

## 3 板块：用户偏好（Profile）与有效约束 C

### 3.1 职责

- 维护长期画像（L4 DB）与当轮约束（L3 state）。  
- 产出本轮 `**EffectiveConstraint C`**，供 `search_recipes` 增强查询与后过滤（现有 `SearchRecipesService` 已读 profile；规格要求 **硬约束** 必须在检索结果侧再次兜底过滤，见 §5.4）。

### 3.2 标识符与存储

- **SCOPE_ID**：默认 `default`，配置 `household.default_id`。  
- **画像 SQLite**：路径由配置指定（默认 `data/db/user_profiles.db`）。  
- **表结构（保持兼容，逻辑映射）**：
  - `user_long_term_profile.user_id` **必须** = `SCOPE_ID`
  - `user_short_term_states.user_id` **必须** = `SCOPE_ID`
  - `user_profiles.user_id` **必须** = `SCOPE_ID`（若创建基础行）

实现迁移：若历史数据使用 `default_user`，启动时执行一次性 `**UPDATE … SET user_id='default' WHERE user_id='default_user'`** 或由读取层别名映射（推荐统一到 `SCOPE_ID`）。

### 3.3 长期画像字段（逻辑）


| 字段                         | 类型        | 合并策略            |
| -------------------------- | --------- | --------------- |
| allergens                  | List[str] | 被动：并集去重；显式修正：替换 |
| medical_restrictions       | List[str] | 同上              |
| dietary_target             | str       | 被动：空则填；显式：可覆盖   |
| taste_like / taste_dislike | List[str] | 被动：并集；显式：按字段替换  |
| cooking_habits             | List[str] | 被动：并集           |


Keeper 输出 `**intent_type**`：`passive_extract` | `explicit_correction`，与 SRS FR-12 一致。

### 3.4 短期状态（TTL）

- 表 `user_short_term_states`：`expires_at` 默认创建时间 + **7 天**（与现有 `DEFAULT_SHORT_TERM_TTL_DAYS` 一致，可配置）。  
- 查询活跃状态：`get_active_short_term_states(SCOPE_ID)`，过滤 `expires_at` 与 `is_active`。

### 3.5 有效约束 C（内存对象，建议 TypedDict / Pydantic）

```python
# 示意
class EffectiveConstraint:
    scope_id: str                    # SCOPE_ID
    hard_exclusions: list[str]       # 过敏原 + 医嘱禁食食材关键词
    soft_negative_hints: list[str]   # 讨厌食材等，用于排序/话术
    soft_positive_hints: list[str]   # 口味偏好
    dietary_target: str | None
    temporal_conditions: list[str]   # 来自 L3 short_term_constraints
    summary_snippet: str | None      # 可选：来自 L2 摘要片段供 LLM
```

**合并算法（必须）**：

1. 读 `user_long_term_profile` + `user_short_term_states` + `memory_state.short_term_constraints`。
2. `hard_exclusions` = allergens ∪ medical 映射出的禁食列表 ∪（可选）从 temporal 解析出的临时禁食关键词。
3. `temporal_conditions` = L3 列表 ∪ DB 短期 active 条件文本。
4. 检索前将 **C** 注入 `search_recipes` 的 query 增强与结果过滤（现有代码 partial；规格要求 **硬排除** 对返回候选再次过滤，见 §5.4）。

## 4 板块：系统记忆（L1～L4）

### 4.1 分层定义


| 层   | 存储                        | 更新时机                               |
| --- | ------------------------- | ---------------------------------- |
| L1  | `messages` + checkpointer | 每轮用户输入追加                           |
| L2  | `conversation_summary`    | 超阈值压缩（参数配置）                        |
| L3  | `short_term_constraints`  | 每轮在 router 前由 **short_term 节点** 写入 |
| L4  | user_profiles.db          | **主回复生成完成后** 异步写入                  |


### 4.2 L2 摘要节点（必须）

- **仅** 更新 `messages` 裁剪与 `conversation_summary`。  
- **禁止**：修改 `task_stack`、`recipe_state`、`inventory_state` 中与澄清相关的字段。

### 4.3 L3 当轮约束节点（必须）

- **输入**：最新用户句 + 可选上一轮上下文。  
- **输出**：`memory_state.short_term_constraints`（`List[str]` 或结构化列表）；可选 `memory_confidence`。  
- **规则示例**：关键词「肠胃」「感冒」「清淡」「忌口」等写入；具体词典可配置。

### 4.4 L4 Keeper（必须）

- **触发**：每轮可在回复完成后执行（见 §4.6）。  
- **输入**：最近窗口消息（如最近 6 条格式化为文本）+ `get_user_profile(SCOPE_ID)`。  
- **输出**：写长期表 / 短期表；**不向用户抛出异常**。

### 4.5 L4 异步执行（已定稿）

- **行为**：在 generator 节点完成状态更新并得到待发送给用户的内容后，调用  
`asyncio.create_task(run_memory_keeper_safe(state_snapshot))`。  
- **快照**：传入不可变快照（scope_id、messages 片段、当前线程上下文），避免并发改 state。  
- **异常**：任务内 `try/except`，记录结构化日志（`error_code=MEMORY_KEEPER_FAILED`），**禁止** 影响已返回的回复。

### 4.6 编排顺序（强制）

```
用户输入 → L1 追加
        → L2 maybe_compress
        → L3 extract_short_term
        → router → … → generator
        → （回复就绪）asyncio.create_task(L4 keeper)
```

## 5 板块：菜谱检索与权威 R（阶段一 + 阶段二）

### 5.1 阶段一：候选与 file_ref

1. 调用 MCP `search_recipes`，`user_id` **必须** 传 `SCOPE_ID`（或与现有 `default_user` 映射一致直至移除）。
2. 应用 **C** 做 query 增强（现有逻辑保留）。
3. **置信规则**（可调配置）：
  - `len(recipes)==1` → 高置信，锁定 `title = recipes[0].title`。  
  - `len(recipes)>=2`：若 \frac{s_1 - s_2}{s_2+\epsilon} > 0.15（与现有 researcher 一致）→ 高置信锁定 top1；否则 **歧义** → `recipe_state.recipe_candidates` + `TASK_CLARIFY`，**不** 调用阶段二。
4. 高置信：调用 `get_recipe_source(recipe_name=锁定 title)` → 得到 `recipe_file_ref`（字符串路径或失败）。

### 5.2 阶段二：权威 R（强制）

**输入**：`recipe_file_ref` 指向的 UTF-8 Markdown 文件路径。

**读取**：使用同步 `open(path, encoding='utf-8')` 或异步等价，读取**全文** `raw_md`。

**解析管线（当前实现基线）**：

- 使用 **LLM + `StructuredRecipe`**（`[src/agent/nodes/schema.py](f:/WHAT-TO-EAT-AGENT/src/agent/nodes/schema.py)`：`title`, `ingredients[].name|amount|unit`, `steps[]`）对 `**raw_md**` 做结构化抽取。  
- **禁止**：仅用 `search_recipes` 返回的 **content 片段**作为 `StructuredRecipe` 的唯一输入。

**输出**：`recipe_state.recipe_requirements = [ {name, amount, unit}, … ]`（即 **R**）；`recipe_steps`；`recipe_title_locked`。

**失败**：文件不存在、读失败、LLM 失败 → `error_state` + 用户可见降级话术；**R** 为空列表时不执行购物清单扣减链路。

### 5.3 语料格式契约（Markdown v1）

仓库菜谱为 Markdown，典型结构（摘自 `data/recipes/**/**.md`）：

- 一级标题：`# 菜名`  
- 小节：`## 必备原料和工具`、`## 计算`、`## 操作` 等。  
- 用料常以列表或「食材：量」形式出现在 `**## 计算`** 附近。

**解析器版本**：`recipe_parser_version = "llm_structured_v1"`（后续可增加 `deterministic_md_v2`）。  
**验收**：对给定 `南派红烧肉.md` 全文的解析 **必须** 产出非空 `ingredients`（允许 LLM 估算「适量」为数值）。

### 5.4 硬约束过滤（检索后兜底）

在阶段一返回的 `recipes` 列表上，对每条候选（若有全文则不现实；对 title/metadata）执行：

- 若 **C.hard_exclusions** 中任一关键词命中菜名或（可选）摘要字段 → **剔除**该候选。  
若剔除后为空 → 走 **检索无结果** 分支（降级话术；与购物清单 §7 无关）。

## 6 板块：库存（Inventory）

### 6.1 职责

提供 **I**：`Dict[ingredient_name, {amount, unit}]`；支持查询、补货、确认扣减。

### 6.2 表结构（目标 Schema）

**当前代码**为 `inventory(name PRIMARY KEY, …)`。**目标**（迁移必须完成）：

```sql
CREATE TABLE inventory (
  household_id TEXT NOT NULL DEFAULT 'default',
  name         TEXT NOT NULL,
  amount       REAL NOT NULL DEFAULT 0,
  unit         TEXT NOT NULL,
  updated_at   TEXT NOT NULL,
  PRIMARY KEY (household_id, name)
);
```

- 迁移：`INSERT SELECT` 时 `household_id = SCOPE_ID`。  
- 所有 API：`WHERE household_id = ?`。

### 6.3 扣减时机（已定稿）

**产品语义**：扣减发生在用户 **已确认使用（采纳）与当前会话锁定的菜谱** 之后；不得在未绑定菜谱的情况下按「刚推荐的菜」写库扣减。

**必须同时满足**后方可执行 `batch_deduct`：

1. `recipe_state.recipe_requirements`（**R**）非空，且与当前锁定菜一致；  
2. `inventory_state.recipe_use_confirmed == True`（由用户明确话术或选项确认置位，例如「就用这道」「确认用红烧肉」）；  
3. 意图为 `inventory_commit` 或等价 `TASK_INV_COMMIT`（可与「确认使用菜谱」**合并为同一轮**用户输入，由路由解析为连续动作：先置 `inventory_state.recipe_use_confirmed`，再执行扣减）。

**禁止**：

- 仅凭检索/推荐完成即自动扣减；  
- `recipe_use_confirmed` 为假时执行 `batch_deduct`。

**交互**：若用户仅确认做菜谱但未说扣减，可追问「要按这份菜谱从库存扣减吗？」；用户确认后再入队 `TASK_INV_COMMIT`。

### 6.4 失败语义（扣减）

- 任一批量扣减写失败：`commit_status=failed`，回复中明示；禁止返回成功措辞（FR-32）。  
- 补货写失败见 §6.5.5。

### 6.5 补货（增加）时机与流程

#### 6.5.1 与扣减的差异

| 维度 | 扣减（§6.3） | 补货（本节） |
| --- | --- | --- |
| 是否绑定菜谱 | **必须** `recipe_use_confirmed` + **R** | **否** |
| 典型意图标签 | `inventory_commit` / `TASK_INV_COMMIT` | `inventory_add` / `restock`（或路由映射的等价标签） |
| 状态字段 | `commit_preview` / `commit_status` | `add_preview` / `add_status` |

#### 6.5.2 触发时机（允许入口）

1. **主路径 — 自然语言补货**：用户明确表达「买了 / 进了 / 补货 / 刚拎回家」等，且可解析出 **食材 + 数量 + 单位**（或经一轮澄清后补齐）。  
2. **次路径 — 购物清单闭环**（可选阶段实现）：用户在已有 `cached_shopping_gap`（§7）前提下，表达「清单上的都买了」「鸡蛋和牛奶买好了」或（UI 若有）对缺口行标记「已买」；系统将对应行映射为入库项，**仍须**走 §6.5.3 预览与确认（可与多行合并为一次确认）。

**禁止**作为补货触发：

- 仅完成菜谱检索或推荐，**自动**写入库存增加；  
- 未解析出稳定的 `(name, amount, unit)`（或等价结构）即写库；  
- 将 L4 记忆 Keeper 的被动抽取 **默认** 等同为已落库 **I**（若未来从对话抽取补货线索，只能进入 `add_preview` 草稿，**必须**经用户确认后再写库）。

#### 6.5.3 处理流程（必须）

1. **解析与规范化**：食材名经 §7.5 `normalize_name`；数量与单位经 `UnitConverter` 或与扣减一致的单位策略；无法换算或语义含糊 → **澄清**或记入 `add_preview.unresolved[]`，**禁止**猜测写库。  
2. **合并语义**（每条入库须指定其一，由路由/解析决定）：  
   - **`merge_mode=add`**：在现有 `inventory.amount` 上 **累加**（默认，适用于「买了两斤」）；  
   - **`merge_mode=set`**：将库存 **设为**给定绝对值（适用于「家里鸡蛋现在一共 12 个」等整表式表述）。  
3. **预览**：写入 `add_preview`，建议结构：  
   - `items: List[{ name, delta_or_value, unit, merge_mode }]`；  
   - 可选 `source: utterance | shopping_gap`，便于审计。  
4. **确认**：向用户展示预览文案；用户 **明确确认** 后执行持久化。  
   - 配置项 `inventory.restock.confirm_required`（默认 `true`）：为 `true` 时 **禁止** 跳过确认；为 `false` 时仅允许在 **单条、高置信、单位已标准化** 等条件下免确认（具体阈值实现自定，须在路由或 logistics 中单一真相源）。  
5. **写库**：对 `household_id = SCOPE_ID` 执行 upsert / 增量更新；`add_status`：`pending` → `success` | `partial_success` | `failed`。  
6. **批次**：多食材一次买入 → 单一 `add_preview` 列表 + **一次**确认；若批量写库部分失败，回复中 **逐条** 标明成功与失败（FR-32）。

#### 6.5.4 与缺口缓存的衔接

- 补货 **成功** 后：视为 **I** 变更，**必须** 更新 `gap_basis.inventory_fingerprint` 并按 §7.1 **重算** `cached_shopping_gap`（可与扣减共用同一失效逻辑，见 §7.6）。  
- 从购物清单入口映射的条目，优先使用缺口行中已有 **建议采购量** 作为 `delta_or_value`（若用户未改口）；单位不一致时按换算规则或澄清。

#### 6.5.5 失败语义（补货）

- `add_status=failed` 或 `partial_success`：回复中明示；禁止整体成功措辞（FR-32）。  
- 可与 `error_state.error_code` 联动，例如 `INVENTORY_ADD_UNPARSED`（解析失败）、`INVENTORY_WRITE_FAILED`（写库失败）。

## 7 板块：购物清单（Gap）

### 7.1 预计算与缓存（静默）

**触发**：**R** 已由 §5.2 产出且非空，**且** 已从 DB 拉取 **I**（`get_all` 带 `household_id` / `SCOPE_ID`）。

**行为**：

1. 使用 §7.3 规范化后执行 §7.2 计算。  
2. 将完整结果写入 `inventory_state.cached_shopping_gap`。  
3. 写入 `gap_basis`：  
   - `recipe_title` = `recipe_title_locked`；  
   - `r_fingerprint` = 对 **R** 稳定序列化（如规范化后 JSON 或 hash）；  
   - `inventory_fingerprint` = 对 **I** 稳定序列化或 `updated_at` 聚合值（实现任选，须能检测库存变更）。

**不要求**用户本轮含有清单意图；**禁止**因此强制在回复中输出完整购物清单（除非用户意图或场景需要，如 S-03）。

### 7.2 计算结构

- 使用现有 [`UnitConverter.gap`](f:/WHAT-TO-EAT-AGENT/src/libs/utils/unit_converter.py) 逐项计算。  
- `cached_shopping_gap` **建议字段**：`shopping_list`, `sufficient_items`, `missing_items`, `pending_manual[]`, `computed_at`（时间戳）。

### 7.3 显式索要清单时的交付

当意图分流命中「清单」或用户明确要求「缺什么/买啥/购物清单」等：

1. **若** `gap_basis` 与当前 **R**、**I** 一致（指纹匹配）且 `cached_shopping_gap` 非空 → **直接**以缓存结果 + `shopping_list_overlay` 合并展示（§7.4），**不应**无理由重复全量计算。  
2. **若** 缓存缺失或已失效 → 执行 §7.1～7.2 重新计算并更新缓存，再展示。  
3. 向用户说明时，可简短提示「按当前菜谱与库存算的缺口」；若曾应用用户编辑，可提示「已包含你改过的条目」。

### 7.4 对话中的清单修改（编辑层）

**目标**：用户在多轮对话中可调整「要买什么」的呈现，而不一定等于原始 `shopping_list`。

**`shopping_list_overlay` 建议结构**：有序操作列表，例如：

- `{ op: "remove", key: "<规范化食材名或行 id>" }`  
- `{ op: "add", display: "酸奶 2 盒", note?: str }`  
- `{ op: "adjust_note", key: "…", note: "改买低脂" }`

**合并规则**：

1. **展示** = 以 `cached_shopping_gap.shopping_list`（及 `pending_manual`）为底，按 `overlay` 顺序应用；用户 **remove** 的项不再展示；**add** 追加为独立行并标记来源 `user`。  
2. **重新预计算**（刷新 `cached_shopping_gap`）后：若实现策略为「编辑尽量保留」，可对仍存在于新缺口中的项保留 `adjust_note`；对已不存在的项丢弃并 **可** 提示用户。  
3. 用户可说「按菜谱重新算清单」类话术 → 清空 `shopping_list_overlay`（或标记忽略），执行 §7.2 并写回缓存。

### 7.5 食材名称规范化（已定稿 v1）

**函数** `normalize_name(s: str) -> str`：

1. `strip()`
2. 全角数字字母转半角（可选库或简单表）
3. 查 `config/ingredient_aliases.yaml`（若存在）：同义词映射到 **canonical**
4. **不** 做简繁转换（除非配置开启）

**R 与 I 比对前**双方均过 `normalize_name`。

### 7.6 与 §5.2、§6 的衔接

- **R** 解析失败或为空：不写有效 `cached_shopping_gap`（可置空并记录错误码）；扣减链路不启用。  
- **I** 变更**后**（补货、扣减成功）：**必须**更新 `inventory_fingerprint` 并触发 **§7.1 重算**（可在同一事务或下一用户轮 lazy 重算，但用户索要清单时结果须与最新 **I** 一致）。

## 10 端到端测评（E2E）：流程、分层指标、业务链路树与产出物

本节为 **垂类膳食助手** 自动化端到端测评的技术规格，与 [`docs/开发计划.md`](开发计划.md) **§5～§6**、**§3 T-040～T-043**、[`docs/项目说明.md`](项目说明.md) **§10**、**NFR-08～NFR-11** 对齐。**不**替代单测与 `docs/test_report.md`。

### 10.1 定位与标识

- **对象**：真实 Agent（与线上一致配置）；**输入**：按 **场景分类** 组织的用例数据（YAML/JSON 等，`case_id`、`scenario_category`、多轮 `user_turns`、`expected`）。  
- **流程**：跑批 → 与期望对比 → **自动打分** → 每用例 **业务链路树**（§10.5）→ 全量 **测评总报告**（§10.6）。  
- **标识**：`run_id`、`thread_id`/`session_id`（若与 checkpointer 对齐）、与 SRS §3.2 **S-01～S-08** 的可选映射。

### 10.2 批跑流程（与开发计划 §5.0 一致）

1. **构造**：维护用例集（YAML/JSON），`expected` 至少支持意图/槽位、金标菜谱 id、可选 **R** 金标、澄清期望、多轮忌口/偏好断言等。  
2. **执行**：对每条用例调用 `create_agent` / `run_turn`（或等价封装），采集 **检索候选、控制面、`recipe_state`、解析 **R**、最终回复、耗时、token（若可得）、工具调用次数**。  
3. **对比与打分**：按 **§10.3** 计算分层指标并与 `expected` 对比；按 **开发计划 §5.6** 合成用例总分。  
4. **单用例报告**：Markdown（及可选 JSON），**必须** 含 §10.5。  
5. **测评总报告**：全部用例结束后输出 §10.6。

### 10.3 分层指标体系（实现须可计算、报告须可展示）

#### 10.3.1 检索层

| 指标 | 规格化含义 | 采集来源 |
| --- | --- | --- |
| **召回率** | `expected.golden_recipe_ids`（或等价）是否出现在 `search_recipes` 候选（或管线等价输出）中；多金标可定义 Hit@k | MCP 返回、`recipe_state` 候选列表 |
| **排名** | 金标在排序列表中的 **名次**（1-based） | 同上 |
| **MRR** | 多查询/多用例集上对「首个金标命中位次」的倒数之均值 | 由单条排名聚合 |
| **NDCG@k** | 若用例提供 **分级相关性标注**，对候选列表计算 NDCG；**无标注时报告 N/A**，不得伪算 | fixture 可选字段 |

#### 10.3.2 生成层

| 指标 | 规格化含义 | 采集来源 |
| --- | --- | --- |
| **准确性** | 解析 **R** 或展示结构与金标在 **营养相关字段、步骤条数/顺序、食材集合** 等约定字段上的一致性（容差策略须文档化） | 阶段二 **R** vs fixture 金标 |
| **幻觉率** | 生成文本或结构化字段中出现 **不可被 R+库内事实支持** 的食材、步骤、营养表述之比例或二值标志 | 最终回复 + **R** |
| **格式合规** | 输出是否符合约定 schema（如 `StructuredRecipe`）；纯文本场景退化为「必选片段/列表项」规则 | schema/规则校验 |

#### 10.3.3 对话层

| 指标 | 规格化含义 | 采集来源 |
| --- | --- | --- |
| **意图识别准确率** | 路由输出的 `intents`/主意图与 `expected` 是否一致（可分意图宏平均） | `control_state` 落盘或路由快照 |
| **澄清触发率** | **歧义标注**用例上是否出现澄清（`needs_clarification`、澄清任务或澄清话术）；**非歧义**用例上是否误触发 | 控制面 + `task_stack` |
| **上下文保持率** | **多轮**用例中，后续轮状态或回复是否仍体现首轮 **忌口/偏好/短期状态**（与 **C**、画像一致） | 多轮 state、回复抽检 |

#### 10.3.4 效率

| 指标 | 规格化含义 | 采集来源 |
| --- | --- | --- |
| **平均响应时间** | 用例级或每轮 wall clock；总报告给全集均值 | 执行器计时 |
| **平均 token 消耗** | 单用例输入+输出 token；不可得则总报告标 **未测** | LLM usage |
| **工具调用次数** | 单用例内 MCP（如 `search_recipes` / `get_recipe_source`）等调用次数，宜区分成功/失败 | 执行器包装或日志 |

### 10.4 期望字段与自动打分（原则）

- `expected` **应** 能表达：**意图/槽位**、可选 **金标菜谱 id**、可选 **R 金标**、**是否期望澄清**、**多轮偏好断言**、**检索必达** 等；实现 **应** 支持缺失字段时子指标 **N/A**（不参与该层均分，总报告说明）。  
- **硬失败**：若用例标记「检索必达」且召回为 0，**宜** 支持封顶分或直接判失败（与 **开发计划 §5.6** 一致）。

### 10.5 单用例「业务链路树」（必选）

每条用例的人类可读物 **必须** 含树状摘要，层级与 **开发计划 §5.5** 一致：**意图识别 → 槽位提取 → 检索调用（query、返回条数）→ 过滤/排序（与真实实现对齐，未实现标 **—**）→ 生成回复**；每节点 **✓ / ✗ / —**，**禁止**将未实现能力写为已通过。

### 10.6 产出物与路径

| 路径 | 必选 | 说明 |
| --- | --- | --- |
| **测评总报告** | **`docs/agent_eval_report.md`** 或 **`docs/evals/e2e_summary_<run_id>.md`**（实现于 T-043 定稿二选一） | 全量跑完 **必须** 生成；须含 **§10.3 各层** 汇总、均分、通过率、失败 `case_id` 列表、本次 `run_id`、可选与历史 run 对比 |
| **manifest** | `docs/evals/runs/<run_id>/manifest.json` | **宜**：列出 `case_id`、`scenario_category`、单用例报告路径、原始采集 JSON 路径 |
| **单用例报告** | `docs/evals/cases/<run_id>/<case_id>.md`（及可选 `.json`） | **必须**：§10.5 链路树 + 期望/实际摘要 + 分层子得分与用例总分 |
| **机器可读分数** | `docs/evals/latest_eval.json` 或 `docs/evals/runs/<run_id>/scores.json` | **宜**：供 CI diff |

**与 `docs/test_report.md`**：单测/TR 记录 **测对/测错**；本组记录 **E2E 分层得分与体验**，可交叉引用 TR，**职责不合并**。

### 10.7 与生产可观测、可选调试轨迹

- **NFR-06 / T-028**：生产环境 `agent.node_span` 等为持续可观测；E2E runner **可** 另存 MCP/节点级调试序列，**不强制**固定 `steps[]` schema；若落盘，**禁止**记录密钥。  
- **入口**：测评 runner **须** 独立于产品 `main.py`（与开发计划 §6 末一致）。**Agent 系统端到端测评不得**以 pytest 作为跑批主入口（与仓库 `tests/` 单测分层；CI **应**调用独立 CLI / `python -m …`，而非 `pytest -m …` 驱动全图）。

## 12 意图识别与槽位填充（Slot Filling）

本节定义**槽位填充式**意图识别的**输出契约**：每轮在结构化结果中同时给出 **意图标签（可多选）**、**统一槽位表 `slots`**、**综合置信度**与 **是否需澄清**。实现可继续将 `slots` 序列化进现有 `entities: Dict`（逐步收敛字段名），但**语义**以下表为准。

### 12.1 输出对象（逻辑 schema）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `intents` | `List[str]` | 有序；**越前表示仲裁优先级越高**（对齐 FR-50 时再细化为同轮执行顺序） |
| `primary_intent` | `str` | 与 `intents[0]` 一致（兼容旧字段 `current_intent`） |
| `confidence` | `float ∈ [0,1]` | 对「意图组合 + 槽位整体」的综合置信度 |
| `slots` | `Dict[str, Any]` | **全局槽位命名空间**（§12.2）；禁止用零散自由 key 替代 |
| `missing_slots` | `List[str]` | 本轮**仍未填满**的槽位名；用于澄清话术与 `needs_clarification` |
| `needs_clarification` | `bool` | `confidence` 低于阈值（§12.6）或 **必填槽缺失** 时为 `true` |

**入 `AgentState`**：路由将 `confidence`、`slots`、`missing_slots`、`needs_clarification` 写入 **`control_state`** 同名键；将 `intents` 映射为 `control_state.primary_intent`（=`intents[0]`，若为空则 `None`）与 `control_state.secondary_intents`（=`intents[1:]`），**禁止**与扁平 `current_intent` 长期双真相。

**与任务栈**：路由将 `(intents, slots)` 映射为 `control_state.task_stack`（§12.4）；**执行即出队**语义见 FR-04。

### 12.2 全局槽位（跨意图复用）

下列槽位构成**唯一推荐命名**；LLM 或规则解析均应**回填到此命名空间**（历史别名见「兼容」列）。

| 槽位 key | 类型 | 含义 | 规范化 / 备注 |
| --- | --- | --- | --- |
| `recipe_query` | `str \| null` | 开放式找菜用语（风格、场景、营养目标等） | 可原样进检索 query |
| `recipe_name` | `str \| null` | **指名**具体菜名（如「红烧肉」） | 与 `recipe_title_locked` 对齐前为候选文本 |
| `ingredients` | `List[str]` | 用户提到的食材名列表（未带量） | 经 §7.5 `normalize_name` 后再写业务状态 |
| `restock_items` | `List[{name, amount, unit, merge_mode?}]` | **补货**结构化行；`merge_mode`：`add` \| `set`，缺省 `add` | 对应 §6.5；`amount`/`unit` 须能进单位体系或进 `unresolved` |
| `recipe_name_for_commit` | `str \| null` | **扣减**时用户声明已完成/要扣的那道菜 | 须与当前锁定菜或可解析候选对齐，否则澄清 |
| `inventory_query_targets` | `List[str] \| null` | 用户问「有没有」的具体食材；`null` 表示查「全部/家里有什么」 |  |
| `profile_fragments` | `List[str]` 或结构化对象 | 画像相关自然语言片段（过敏、忌口、喜好） | 交由 `TASK_PROFILE_SYNC` / Keeper 策略消化 |
| `profile_explicit` | `bool` | 是否显式「记住/更新偏好」类表述 | `true` 时倾向 `explicit_correction` |
| `list_action` | 枚举字符串 | 购物清单：`show`（要看清单）\| `edit_overlay`（改清单呈现）\| `refresh_gap`（按菜谱重算）\| `mark_bought`（从缺口标记已买 → §6.5.2） | 缺省 `show` |
| `list_edit_ops` | `List[dict]` | 与 §7.4 `shopping_list_overlay` 同构的操作序列（可选由 LLM 预填） | 仅当 `list_action=edit_overlay` 时重点使用 |
| `recipe_adoption` | `bool` | 用户是否表达 **采纳当前锁定/候选菜谱**（「就做这个」「用第一道」） | 为 `true` 时置 `inventory_state.recipe_use_confirmed`（§6.3） |
| `deduct_confirm` | `bool` | 是否在采纳菜谱之外 **明确同意扣库存** | 与 `inventory_commit` 联用 |
| `diet_topic` | `str \| null` | 膳食/营养咨询子主题 | 供 `dietary_advice` 生成回复 |

**兼容别名（实现迁移期）**：现有 `entities.amounts`（`Dict[str,str]`）视为 `restock_items` / 历史补货的扁平来源，须在 logistics 入口 **归一**为 `restock_items`；`check_inventory` 布尔可弃用，以 `inventory_query_targets` 非空或「查全部」规则替代。

### 12.3 意图标签目录（产品级）

**元意图**（不直接映射写库重任务；通常 `TASK_DIRECT_REPLY` 或系统澄清）：

| 意图 ID | 说明 |
| --- | --- |
| `meta_clarify` | 系统侧：置信低或必填槽缺失，**非**用户闲聊（可由路由不写 LLM，直接 `needs_clarification=true`） |
| `help` | 使用帮助、能做什么 |
| `out_of_scope` | 明确超范围 |
| `general_chat` | 闲聊（与膳食弱相关或无关） |

**业务意图**：

| 意图 ID | 说明 | 典型槽位 |
| --- | --- | --- |
| `profile_sync` | 长期/短期画像写入或显式修正 | `profile_fragments`, `profile_explicit` |
| `recipe_search` | 找菜、推荐、指名菜谱、按食材做菜 | `recipe_query`, `recipe_name`, `ingredients` |
| `recipe_adopt` | **确认采纳**当前会话中的锁定/候选菜谱（§6.3 前置） | `recipe_adoption=true`，可选 `recipe_name` 消歧 |
| `inventory_check` | 查询库存 | `inventory_query_targets` |
| `inventory_add` | 补货入库（§6.5） | `restock_items`（或迁移期 `entities.amounts`） |
| `inventory_commit` | 确认 **使用菜谱并扣减**（可同轮含 `recipe_adopt`） | `recipe_name_for_commit`, `deduct_confirm`, `recipe_adoption` |
| `shopping_list` | 要看/改/重算清单、从清单标记已买 | `list_action`, `list_edit_ops` |
| `dietary_advice` | 营养/健康类问答（不必然触发检索） | `diet_topic`, `ingredients` |

**与代码常量对齐**：`src/agent/nodes/schema.py` 中 `IntentResult.intents` **应扩展**包含上表中的 `recipe_adopt`、`help`、`out_of_scope`（及可选 `meta_clarify` 若改为模型输出）；`src/agent/nodes/router.py` 的 `INTENT_TASK_MAPPING` **应补全** `dietary_advice` → `TASK_DIRECT_REPLY`，并新增 `recipe_adopt` → `[]` 或 `TASK_DIRECT_REPLY`（仅置状态位，不写 MCP）。

### 12.4 意图 → 任务栈映射（规范）

| 意图 | 映射 `task_stack`（默认；有序） | 说明 |
| --- | --- | --- |
| `profile_sync` | `[TASK_PROFILE_SYNC]` |  |
| `recipe_search` | `[TASK_SEARCH]` | 歧义时由 researcher 追加 `TASK_CLARIFY`（现有逻辑） |
| `recipe_adopt` | `[]` 或 `[TASK_DIRECT_REPLY]` | **必须**更新 `inventory_state.recipe_use_confirmed`，不触发检索 |
| `inventory_check` | `[TASK_INV_CHECK]` | 常与 `recipe_search` 同轮共存，顺序遵守 FR-50 |
| `inventory_add` | `[TASK_INV_ADD]` |  |
| `inventory_commit` | `[TASK_INV_COMMIT]` | 若槽位显示尚未采纳菜谱，可先内部等价 `recipe_adopt` 再扣减（同一轮） |
| `shopping_list` | `[TASK_GAP_CALC]` | 展示/合并编辑/重算在 logistics 内按 `list_action` 分支 |
| `dietary_advice` | `[TASK_DIRECT_REPLY]` |  |
| `help` / `out_of_scope` / `general_chat` | `[TASK_DIRECT_REPLY]` | 提示词分支区分 |
| `meta_clarify` | `[TASK_CLARIFY]` 或由路由直接生成澄清 | 与菜谱歧义澄清共用机制时须区分 **槽位澄清** vs **选菜澄清**（可用 `control_state` 子类型） |

**多意图示例**（与 FR-50 一致）：  
「想吃红烧肉，家里肉够吗」→ `recipe_search` + `inventory_check`；  
「就用红烧肉，扣库存」→ `recipe_adopt` + `inventory_commit`（或合并解析为 `inventory_commit` + `deduct_confirm` + `recipe_adoption`）。

### 12.5 分意图必填槽（最小集合）

以下为 **V1 产品约束**：缺失则 `missing_slots` 须列出，并 **应** 触发澄清而非盲写库。

| 意图 | 必填槽 | 可选槽 |
| --- | --- | --- |
| `recipe_search` | `recipe_query` **或** `recipe_name` **或** 非空 `ingredients`（三者至少其一） | `recipe_query`+`recipe_name` 同时存在时以 `recipe_name` 优先指名 |
| `recipe_adopt` | 会话中已有可解析的候选/锁定菜；否则需 `recipe_name` | `recipe_name` |
| `inventory_check` | 无（空目标表示查全景） | `inventory_query_targets` |
| `inventory_add` | `restock_items` 至少一条且 `amount+unit` 可解析 **或** 进入澄清 | `merge_mode` |
| `inventory_commit` | `recipe_name_for_commit` 与当前 **R** 绑定一致；且逻辑上 `recipe_use_confirmed` 可为真（本意图或同轮 `recipe_adopt`） | `deduct_confirm` |
| `shopping_list` | 依赖 **R** 已稳定（§7）；若仅有清单意图而无 **R**，应先 `recipe_search` 或沿用会话已锁定 **R** | `list_action`, `list_edit_ops` |
| `profile_sync` | 非空 `profile_fragments` 或可抽取的等价结构 | `profile_explicit` |
| `dietary_advice` | `diet_topic` 或用户句足够自包含 | `ingredients` |

### 12.6 澄清与置信度

- **槽位澄清**：`missing_slots` 非空时，生成器应追问 **仅针对缺失槽**（与 `TASK_CLARIFY` 菜谱列表澄清 UI 区分）。  
- **置信度阈值**：配置 `intent.confidence.clarify_threshold`（建议初值 `0.55`）；`confidence` 低于阈值 → `needs_clarification=true`，**禁止**触发 `TASK_INV_COMMIT` / `TASK_INV_ADD` 写库。  
- **安全**：涉及硬禁忌/医嘱的 `profile_sync`，低置信时 **应** 二次确认再落库（SRS FR-11）。

### 12.7 与你「一起设计」时的扩展位

以下能力 **V1 可简化**，槽位预留即可：

- **多成员**：`target_member_id`（当前单机可恒为 `SCOPE_ID`）。  
- **时间**：`meal_time` / `date`（计划餐次）。  
- **设备**：`cooking_tool`（空气炸锅等）— 可并入 `recipe_query`。

若你确认要支持「单轮只采纳菜不扣减」与「先扣减再发现未采纳」的互斥规则，保持 **`recipe_adopt` 与 `inventory_commit` 槽位分离**即可，无需再拆意图。
